1. What it is

The built-in Home Assistant assistant recognizes sentences using templates: HA intents, your own sentences in custom_sentences and automations with a sentence trigger. It is fast and reliable, but as soon as you phrase something differently (“What time does Olivia go to school tomorrow?” instead of “When do Olivia's lessons start?”), you hear “Sorry, I couldn't understand that”. Adding more and more sentence variants never ends.

Assist Router is a conversation agent layered on top of the built-in HA agent. Everything HA understands keeps working unchanged. When HA does not recognize a sentence:

  • a small language model (e.g. Gemma 4 E4B in Ollama) only recognizes the topic of the question, e.g. “school” or “car”. This takes about half a second;
  • the integration fetches real data from HA for that topic: entity states, their attributes (e.g. a school timetable) and service responses (calendars, forecast), trimmed to the person and day mentioned in the question. You do not need to write any automations for this;
  • the answer model writes an answer to the question asked based solely on that data: “Olivia finishes at 12:40 today, so she is at school for 5 hours and 10 minutes”;
  • general knowledge questions (“Who was Copernicus?”) get a 3–4 sentence summary of a Wikipedia article;
  • commands that HA does not know literally (“make it brighter in the living room”, “lower the blind halfway”) are parsed into an HA intent and executed. When the assistant is not sure, it asks first (“Should I turn off the kitchen light?”);
  • everything else (chit-chat, jokes) is handled by the fallback agent of your choice;
  • every unrecognized sentence is written to a CSV file. It shows what was said, what the assistant answered and which path the router took.

2. How it works

Why the router returns only the topic

Small models make mistakes when they have to pick the topic, the person and the day and call a tool all at once. That is why the work is split like this:

  • The router model returns a single field in schema-constrained JSON: a topic from the list. It cannot make up a value that is not on the list.
  • The code extracts from the question the people (names including inflected forms - in Polish „Oli”, „Olą” for „Ola”), the day (“tomorrow”, “the day after tomorrow”, “at the weekend”; the words come from the language pack) and the Wikipedia search term. This is reliable and instant.
  • Home Assistant supplies the data, and the answer model only reads, calculates and compares it.

As a result, answers are not made up, and a small model is enough for most tasks. The same split applies to home control: the model picks the intent and parameters from lists, the code matches the device, and HA executes the action.

Knowledge questions (Wikipedia)

  1. Search term. The code strips the beginning of the question (“who was”, “what is”, “who is currently”, “who wrote / invented / won”, “where is”…; the phrases come from the language pack), so only the term itself is sent to the search: “Who wrote Pan Tadeusz?” → “Pan Tadeusz”.
  2. Typos. When the search returns nothing (a misspelled word), the integration takes Wikipedia's spelling suggestion and searches again.
  3. Matching article. The article title must contain a word from the search term - the search engine always finds something, even for gibberish, and we do not read such an article.
  4. Several articles. The model gets the first article (up to 4000 characters) and the introductions of the next two matching ones (1000 each). For “Who is the current world champion…” the first result is the upcoming tournament, while the answer is in the article about the most recent one.
  5. Answer. The model answers the question from these texts in 3–4 sentences.

3. Requirements and models

  • Home Assistant 2026.x (tested on 2026.10) with Assist in a language that has a language pack - Polish today (Whisper and Piper, or other STT/TTS).
  • An Ollama server on the local network. It can run on a different computer than HA. Choose models that understand and write your language well.
  • Optionally a fallback agent, e.g. the Ollama integration with a model for free-form conversation.

Proven in daily use: the whole setup runs every day in the author's home on an NVIDIA Jetson AGX Orin 64 GB: Ollama (Gemma 4 26B as both router and answer model), faster-whisper and Assist Speaker ID. It works very well: the router answers in about 0.7 s and an answer from data (router plus answer model) takes about 2 s. 64 GB of unified memory holds the model alongside Whisper.

If the fallback agent in the Ollama integration uses the same model as the answer model, set its context to 8192 as well. Otherwise Ollama will reload the model on every question.

4. Installation

  1. Copy custom_components/assist_router into the /config/custom_components/ directory. Alternatively, add the repository to HACS as a custom repository of type “Integration”.
  2. Restart Home Assistant.
  3. Settings → Devices & services → Add integration → Assist Router.
  4. Settings → Voice assistants: in every pipeline change the conversation agent to “Assist Router” (entity conversation.assist_router) and turn off “Prefer handling commands locally”. With that option on, HA recognizes built-in intents before Assist Router: an announcement (“Announcement, …”) would be spoken by text-to-speech, and “Who is speaking?” and recording a voice sample would not take priority. Assist Router passes every sentence to the built-in agent first anyway, so nothing is lost.
  5. Copy router.example.yaml from the repository to /config/assist/router.yaml and adapt the entities to your home (file description: section 8). For a Polish household start from router.example.pl.yaml - the same file with Polish descriptions and examples.
  6. In the integration options, enter the Ollama address and choose the models (section 5).
  7. Optionally: Speaker ID, so the assistant knows who is asking (section 7, “Who is asking”). Assist Router reads the speaker by itself; you only need to change speech-to-text in your pipelines.

Example commands for your home

The assist_router.generate_examples action, or the “Example commands” menu item, works like this:

  1. For each topic in router.yaml, the answer model composes sentences using real names: the topic's entities, devices and rooms (for control), and household members.
  2. Every sentence goes through the real router. It is kept only if it lands in its own topic.
  3. Control commands also go through parsing and command planning, without being executed.

Result:

  • the file /config/assist/router_examples.yaml: for each topic its description, working (the sentences that work) and rejected (items with sentence and where it ended up: topic, or control with the reason a command would not work), which hints at which topic description or example to improve. Files written by older versions with the Polish keys dzialaja / odrzucone are still read;
  • the “Example commands” sensor: its state is the number of working sentences, and the topics attribute holds the sentences per topic;
  • a preview in the options.

Generation takes a few minutes, because every sentence is a separate router request. Action options: per_topic (sentences per topic, default 5) and topics (only selected topics). Topics with unclear: true (gibberish) are skipped. The action response gives the working and rejected counts per topic.

The assist_router.clear_log action clears the unrecognized log. The “Unrecognized commands” sensor shows the number of entries, and its last attribute holds the last 20, which is handy for a Markdown card on a dashboard.

6. The router.yaml file

/config/assist/router.yaml describes your home. The integration code is the same for all users. Changes to the file take effect immediately, without restarting HA. Without the file the router is disabled. Below is a skeleton with the most important fields; a full example home with more than a dozen topics is in section 8, and how the code collects and trims data is described in section 7.

# language: pl            # language pack (default: HA's language if there is a pack, otherwise pl)

# Who lives in the home - goes into the router and answer model prompts
household: "Household: Tom (dad), Anna (mom), kids: Olivia, Jack."

# People in questions: match = word beginnings (regex), so inflected forms match too
people:
  olivia: {name: Olivia, match: "oliv|liv\\b"}
  jack:   {name: Jack,   match: "jack"}
  tom:    {name: Tom,    match: "tom|dad"}
  # family: {parents: [tom, anna], children: [olivia, jack], men: [tom, jack]}
  # speaker: voice identifier in Assist Speaker ID (defaults to the person key, here "olivia", "jack")
  # owns: [calendar.olivia] - this person's entities; room: Olivia's room - their room

sentences: 4              # number of sentences in a Wikipedia summary
only_exposed: false       # true = topic entities only from those exposed to Assist
control_model: answer     # which model parses control commands: router or answer
confirm_entities:         # always ask for confirmation (entity_id patterns or names)
  - switch.kitchen_fridge
  - switch.*_enabled
music_players:            # "play …": room -> players, first available wins
  Living room: [media_player.living_room_homepod, media_player.living_room_voice]

topics:
  school:
    description: school, timetable, extra classes, when lessons end
    examples: ["What time does Olivia go to school tomorrow?"]
    details: [sensor.school_timetable]  # entity attributes, trimmed to the person and day in the question
    days: today                         # day code: no day in the question - today
    drop: [teacher, classroom]          # keys to skip

  calendar:
    description: plans, events, meetings, birthdays
    examples: ["What do we have at the weekend?"]
    days: "14"                          # no day in the question - 14 days from today
    fetch:                              # service with a response
      - action: calendar.get_events
        entities: [calendar.family, calendar.work]
        data: {start_date_time: "{start}", end_date_time: "{end}"}
        merge: events                   # one list from all calendars, in order
        title: Calendar events

  car:
    description: car - fuel, range, mileage, is it locked, where is it parked
    examples: ["How much fuel is in the car?", "Did I lock the car?"]
    entities: [sensor.my_car_*, binary_sensor.my_car_*, lock.my_car_*]

  lights:
    description: which lights are on
    entities: [light.*, "!light.ipad_*"]   # "!" = exclusion
    skip_states: ["off"]

  control:
    description: commands - turn on, turn off, set, dim, blinds, warmer, louder
    examples: ["Make it brighter in the living room.", "Lower the blinds halfway."]
    control: true

  knowledge:
    description: a general knowledge question - who was, what is, history, geography
    examples: ["Who was Nicolaus Copernicus?"]
    search: wikipedia

  other:
    description: everything else - chit-chat, jokes, requests
    examples: ["Tell me something interesting."]

Topic keys (school, calendar…) are your own names. Write description and examples in the language your household speaks - the router compares them with the question. With the bundled Polish pack that means Polish (see router.example.pl.yaml).

Answer model prompts

The default prompts are built into the integration. You can override them in router.yaml with the fields answer_prompt (answer from data) and summary_prompt (summary). In the text you can use the fields {household}, {now} (date and time in the pack's language) and {sentences}. The defaults come from the language pack.

7. Where the router gets its data

The router needs no special automations or Assist sentences. It takes data directly from Home Assistant, and in router.yaml you only describe which entities and services belong to a topic. The code does the rest: it picks out what was asked about, removes noise and gives the answer model a concise list of facts.

Three data sources

Topic fieldWhat goes to the modelTypical examples
entitiesThe state of every matching entity, in words, with the most important attributes: light brightness, blind position, thermostat temperature, what is playing, how long a sensor has been open.windows and doors, lights, room sensors, car, people (person.*), motion, alarm, washing machine
detailsEntity attributes, i.e. data you cannot see in the state itself: lists, timetables, balances, addresses.school timetable from the e-gradebook, departures from a stop, phone address (*_geocoded_location), pocket-money accounts
fetchThe response of an HA service that returns data. The day range comes from the question.calendars (calendar.get_events), forecast (weather.get_forecasts)

You can combine all three in a single topic. The weather topic in the example takes the current reading from sensors (entities) and the forecast from a service (fetch).

How the code trims data

  • Person. A list item with a child or person key is kept only if it matches the person in the question (the match pattern from people, so “Olivia” also matches “Liv”). If the person from the question does not appear in the data at all (dad asking about the children's accounts), nothing is removed. A question about “the kids” or without a name gives everyone's data.
  • Day. An item with a date or datetime key is kept only if it falls on the day from the question. If the question gives no day, the topic's days applies. Without days, data is not filtered by day. When there is nothing on that day (lessons on a Saturday), the model gets “none” (Polish pack: „brak”) instead of an empty list. The filter does not apply to the attribute root itself, because there date is usually the reading date.
  • Noise. Skipped: html, avatars, colors, identifiers, friendly_name, false values (“cancelled: no”) and empty values, plus the keys listed in drop.
  • Time. Times with a time zone (forecasts are in UTC) are converted to local time, and the weekday is added next to the date: 2026-10-24 12:00 (Saturday) (the weekday name comes from the language pack - sobota in Polish). The model does not have to work out which day is Saturday.
  • Limits. At most 80 entities in entities (in pattern order, so put the most important first), 40 list items (limit in fetch changes this per service) and 6000 characters per source.

Example: several calendars at once

Without merge, each calendar would be a separate source and the model would have to put the events in order itself. With merge, the question “What do we have on Friday?” gets a ready-made plan for the day, and “When is grandma's birthday?” searches 30 days (days: "30").

fetch safety. The integration only calls services that only return data (in HA: SupportsResponse.ONLY, e.g. calendar.get_events, weather.get_forecasts, todo.get_items). An entry with a service that does something (lock.unlock, a script) is skipped with a warning in the log. A question never switches anything.

What about automations with sentences?

They are not needed. If you already have them, they can stay: HA checks them before the router, so a sentence that exactly matches an automation gets an answer in a fraction of a second, without a model. Any other phrasing goes to the router and the model answers it from the data. The legacy command field (a template question for an automation) still works, but new topics are better described with entities, details and fetch.

Who is asking: recognized speaker (Assist Speaker ID)

With the Assist Speaker ID integration (speech-to-text that also recognizes the voice), the router knows who asked the question. You only need to set its STT (“Speech-to-text with speaker”) in your pipelines. The agent stays Assist Router, which reads the speaker by itself from the same pipeline run. First-person words, family terms and the phrases below are recognized by the language pack (Polish words in brackets).

  • A first-person question without a name (“What classes do I have today?”, “Show my grades”) is about the speaker. details are trimmed to their data, as if their name had been said.
  • A name in the question wins (“What classes does Jack have?” from Olivia gives Jack's timetable). A question without the first person (“What is the timetable?”) stays for everyone. “We have” (Polish „mamy”) is not first person singular.
  • The answer model gets the line “Asking: Olivia.” (Polish pack: „Pyta: …”), so it understands “I” and “my” as that person. The name comes from people, not from Assist Speaker ID.
  • Mapping a voice to a person: the speaker field on the person. It defaults to the person key, so it is enough to save voice samples under the same identifiers (olivia, jack…).
  • Probable speaker (Assist Speaker ID 0.2.0+): the voice did not reach the person's threshold, but the most similar person is close enough (option “Probable speaker from”). Where the answer depends on who asks (first person, personal topics, family terms, “my room”) the router uses that person and says so first: “I think it is Olivia asking. Today you have…” (Polish pack: „Wydaje mi się, że pyta Ola.”, probable_speaker). A recognized speaker is not named; a guess that changes nothing (“What's the weather?”, a name in the question) is not said. The fallback agent never gets a probable name.
  • Unknown speaker (unfamiliar voice, utterance too short, text typed by hand) means everything works as without Assist Speaker ID.

A person's entities and room (owns, labels, room):

  • owns are patterns of entities that belong to the person, e.g. their calendar or their phone's location. When a question is about a specific person (by name, or “I”, “my” from a recognized speaker), other people's entities are skipped in details, fetch and entities. Entities that belong to no one, e.g. the family calendar, are always included. So “What do I have tomorrow?” from Olivia gives the family calendar and her own, without dad's work calendar. This is needed because calendar events have no person field to trim by.
  • labels do the same with Home Assistant labels: give the person labels: [olivia] and put the label “Olivia” on her entities in Settings → Entities (select the entity → labels). Handy for calendars from CalDAV or Google Calendar, which Home Assistant does not link to a person – a new calendar is assigned in the UI, without editing router.yaml. owns and labels can be combined. Set personal: true on the calendar topic, so a recognized speaker gets their own and the shared calendars even without “my” (a parent also gets the children's). When the person asked about has no calendar of their own while others do, the answer model is told so and says it, instead of “there are no events”.
  • room is the person's room. “Turn off the light in my room” from that person means this area.
  • Family terms relative to the speaker (the family section: parents, children, men). “My brother”, “my sister”, “my siblings” from a child, and “my son”, “my daughter”, “my kids” from a parent point to the right people, e.g. “my daughter” from dad means all daughters. They are added to the names in the question (“Are mom and my brother at home?”). “Mom”, “dad”, “wife” and “husband” remain fixed names in match.
  • The fallback agent also gets the line “Asking: Olivia.” in its system prompt.
  • Automation sentences are handled by HA before Assist Router, so they do not get the speaker directly. They can read it from the Assist Speaker ID “Last speaker” sensor, which stays fresh for a few seconds after recognition, e.g. with a macro in custom_templates (see the Assist Speaker ID README).

Daily summary and “good night” for a person: topics with personal: true collect the speaker's data. “Good morning”, “What does my day look like?”, “What's ahead of me today?” from a child give their lessons, tests, chores and calendar. From a parent they give the parent's calendar and the weather, plus a short summary about the kids. How to structure the answer is set by the topic's answer_hint. Example: the daily_summary and good_night topics in router.example.yaml. Scenes with these names are only run when asked explicitly (“Run the Good morning scene”). A plain “Good morning” is a greeting.

Announcements (intercom): a sentence starting with an announcement keyword (Polish pack: „ogłoszenie”, „komunikat”, „do wszystkich”, „intercom”), e.g. “Announcement, kids, please come to dinner”, goes neither to HA nor to the models. Assist Speaker ID plays the speaker's recording, uncut and unchanged, on the other speakers, and the speaker that recorded it only says “Announcement sent.” Additional players, e.g. HomePods, are set in router.yaml as announce_players: [media_player.…]; with Assist Speaker ID 0.1.1+ one speaker plays per room: an available player (e.g. a HomePod) instead of the satellite, and the announcing room gets nothing. Without a recording (text typed by hand or no Assist Speaker ID) the sentence continues along the normal path: HA reads it out with text-to-speech. The keyword must be at the start of the sentence, so “What are the announcements in the school app?” is an ordinary question.

Checking recognition: “Who is speaking?”, “Who am I?”, “How do you recognize me?”, “Whose voice is this?” (Polish pack: „Kto to mówi?”, „Kim jestem?”…). The assistant answers immediately, without HA or models, from the result of that same utterance, e.g. “Olivia is speaking, 82 percent similarity. Next person: Jack, 35 percent.” The answer may also be “I'm not sure”, with the two most similar voices, or “I don't recognize this voice” with the closest person, the similarity that person needs (their threshold) and the next person - e.g. “Closest: Jack, 53 percent, recognition needs 78 percent. Next person: Olivia, 50 percent.” A high threshold usually means somebody else in the household has a similar voice. A short question (under 1 s of speech) gets a request for a longer sentence, e.g. “Tell me who is talking to you now”.

9. How to add a new topic (step by step)

Example: questions about the washing machine and dryer, e.g. “How much longer will the wash take?” or “Can I take the laundry out?”.

  1. Find the entities. Developer tools → States, search e.g. for washing_machine. Check whether the information you need is in the state (e.g. “time remaining: 25 min”) - then entities is enough - or in the attributes (lists, timetables) - then use details.
  2. If the data comes from a service (calendar, forecast), try it in Developer tools → Actions with “Return response” checked. The same action with the same data goes into fetch; use {start} and {end} instead of dates.
  3. Add the topic: 
      laundry:
    description: washing machine, dryer, is the laundry done, how much longer
    examples: ["Is the dryer done?", "How much longer will the wash take?"]
    entities: [sensor.washing_machine_*, sensor.dryer_*]
  4. Save and ask freely. In the CSV file, in the route column, you will see e.g. laundry + 12 encji + odpowiedź (12 entities + answer; the labels come from the language pack), and for details and fetch school + 1 źródeł + odpowiedź (1 source + answer).
  5. If the router picks the wrong topic, improve the description and add the question from the log to examples.
  6. If the answer is wrong but the topic is right, look at what the model received: the data is too long (add drop, days, limit), the answer is missing from it (add an entity), or it contains similar, confusing entities (exclude them with !pattern). tools/compare_sources.py helps (section 12).
Good practices
  • Fewer, clearly distinct topics work better than many similar ones. One “car” topic with all the car's sensors is better than three separate ones.
  • Give the model complete data, e.g. a timetable with the time of every lesson. Then it will also answer questions you did not anticipate (“How many hours is Olivia at school?”).
  • For data with dates, set days so that a question without a day does not pull in the whole week.
  • Put the most important patterns first: the 80-entity limit cuts from the end.

10. Home control

A topic with control: true handles commands that HA did not recognize. hassil sentences and automations always take priority.

The verbs, Whisper corrections, yes/no replies, alarm words and the JSON field names below belong to the language pack. The examples are in English; the Polish words of the bundled pack (languages/pl.py) are given in brackets where the behavior depends on them.

  1. Whisper corrections. Certain corrections of words speech recognition often garbles are applied immediately (Polish: „czystkę” → „wszystkie”, “all”), while uncertain ones (e.g. „jaś” → „zgaś”, “turn off”) trigger a confirmation question. The list is WHISPER_FIXES in the language pack.
  2. Parsing. The model returns schema-constrained JSON. The intent field is an HA intent: HassTurnOn/Off, HassLightSet, HassSetPosition, HassClimateSetTemperature, HassSetVolume/Relative, media control, HassMediaSearchAndPlay (“play …”), vacuum or HassListAddItem. The domain, area and floor fields are chosen from your HA's lists. On top of that come name (a fragment of the utterance), all, value and change (set / more / less), for lights color (e.g. red) and white (color temperature: warm 2700 K, neutral 4000 K, cool 6500 K), and for music query, media class (track, album, artist, playlist, genre, podcast), artist and radio. The key names the model is asked for come from the pack (CONTROL_KEYS; Polish: intencja, domena, obszar, pietro, nazwa, wszystkie, wartosc, zmiana, kolor, barwa, szukaj, rodzaj, wykonawca, radio), because a model fills in fields named in its own language more reliably.
  3. Matching in code.
    • The name fragment is compared with the names and aliases of entities exposed to Assist. Word stems are used, so inflection is not a problem.
    • When the fragment is weak, the device whose name words were all said in the command wins.
    • An area that was not in the utterance is ignored. The model can confuse “in the walk-in closet” with “Garage” (in Polish „garderobie” and „Garaż” look alike).
    • Relative changes (“brighter”, “higher”, “warmer”) are calculated from the current state: by 25% or by 1°.
  4. A confirmation question (“Turn off the closet lighting?”; the conversation stays open for 30 s) is asked when:
    • the Whisper correction was uncertain;
    • the command contains no known verb;
    • several devices match (but not twin entities - see below);
    • it concerns a lock, a gate or a garage door;
    • the device is on the confirm_entities list (also in a group command, e.g. “turn off all switches”).
    With several similarly matching devices (“inner window blind” - small and large) the assistant asks, instead of swapping in another device whose words happened to be said in the command (the outer window blind). Only a device with more words from the command wins (“the lamp in the closet” → Closet Lamp). The question comes in two forms. When uncertain (“Do I understand correctly that I should run Coffee machine - make coffee?”), a plain “no” means “you misunderstood”: the assistant apologizes, asks you to repeat and keeps listening, while “cancel”, “no need” or “stop” end the conversation. For sensitive devices (“Open the front door?”) “no” simply means “do nothing”. Replies work the same way for every question from the assistant. In the Polish pack: yes – „tak” (yes), „dokładnie (tak)” (exactly), „o to (mi) chodzi” (that's what I mean), „działaj” (go ahead), „zrób” (do it), „wykonaj” (execute), „dawaj” (go on); repeat – „nie” (no), „o coś innego” (something else), „nie o to chodzi” (that's not it), „jeszcze raz” (once more), „(może) powtórzę” (let me repeat) – the assistant apologizes and keeps listening; stop – „anuluj” (cancel), „koniec” (stop), „nieważne” (never mind), „zostaw (to)” (leave it), „nic nie rób” (do nothing), „daj (sobie z tym) spokój” (forget it), „olej to” (skip it). For questions about sensitive things (“Open the door?”) a plain “no” means “don't do it” and ends the conversation. A reply with a verb is judged in the context of the question: to “Turn on…?” a plain “turn on” means yes, and “turn off” means no. For locks and blinds the code uses their own verbs (in HA, HassTurnOn for a lock = lock it). Any other utterance cancels the question. Correcting the question: “no” followed by a command is a corrected question – „nie, wyłącz światło w łazience” (no, turn off the bathroom light) or „nie, pytałem czy możesz…” (no, I asked whether you can…). The assistant drops the leading “no” (and lead-ins such as „pytałem czy”, „chodziło mi o” – REPHRASE_LEADS in the language pack) and handles the rest from the start: the HA agent, the router, the models. If that ends with a question again, you can correct it again, as many times as needed – corrections do not count as requests to repeat. A cancel phrase at the start („nie chcę”, „nie rób”) still cancels. The same works after “Sorry, I misunderstood. Please repeat.” The log of unrecognized commands marks such a command with „(poprawione: …)” and the original reply.
  5. Several commands in one sentence – „wyłącz światło w kuchni oraz łazience” (turn off the light in the kitchen and the bathroom), „zamknij rolety w salonie i włącz ekspres do kawy”, „zgaś wszystkie światła oraz włącz alarm”. The HA agent gets the whole sentence first, as always. Only when it does not understand it, and the sentence is a command (a known verb) with a conjunction („i”, „oraz”, „potem”, „następnie”, a comma – CONJUNCTIONS in the language pack), the control model splits it into separate, complete commands, repeating a shared verb or object (split_prompt). Questions are not split („co mają jutro Zosia i Adam” stays one question about two people), nor titles („Simon i Garfunkel”). Each command then takes the whole usual path – HA intents, your sentence automations (e.g. „włącz alarm”), the router – and the replies are joined. A command that needs a question stops there: the assistant says what it has done and asks; the remaining commands wait for the answer and run after „tak” or a correction, „anuluj” drops them. The log of unrecognized commands has one row for the sentence: „kilka poleceń → …”.
  6. Execution via intent.async_handle (HA):
    • Twin entities. A single device is sometimes visible through two integrations under the same name and in the same room, e.g. a HomePod from the Apple TV integration and from Music Assistant (“Bathroom HomePod” ×2). The HA intent rejects such a name (DUPLICATE_NAME) and does nothing, and there is no way to specify an entity_id in it. So the integration does not ask about “several matching devices”; instead it calls the service on each of these entities (media_player.volume_set, homeassistant.turn_on, light.turn_on …); pause and next track - only on the one that is playing. A name given by the model together with the room (“Bathroom HomePod”) is compared without the room word.
    • it checks whether the entity is exposed to Assist;
    • it uses the speaker's room as the default (“turn on the light” without a room);
    • the reply lists what was switched: “Turned off: …”.
  7. Actions: scripts and scenes. The model gets a list of exposed scripts with their descriptions, and of scenes with a list of what they set (HA has no description field for scenes). So a command that does not match any device can still hit an action that does what was asked, even with a garbled word (“make me a coffee” → “Coffee machine - make coffee”, “let's air the flat” → the airing scene). The script is run directly; its fields that select an Assist satellite receive the speaker the command came from.
    • Why a description and not sentences: an automation with sentences only understands the words typed in, while a description tells the model what the script does, so it matches any phrasing. The steps (turn on the coffee machine, wait, brew) are in the script anyway.
    • How to write the description: start with a simple sentence about the effect (“Brews coffee: …”, “Closes all outer blinds: …”) - the model sees the first 160 characters. Add technical details after that.
    • What to expose: only actions meant to be run by voice. Do not expose technical scripts (notifications, updates) or the alarm - the model could pick them by mistake. Add actions the assistant should always ask about to confirm_entities.
    • Automations are not exposed: in HA, “turn on the automation” means “enable it”, not “run it now”. Move an action you want to trigger by voice into a script.
  8. Speech recognition gibberish. Whisper sometimes garbles a whole sentence (Polish: „Głup nastrój w pisarowie” instead of „Włącz nastrój w salonie”, “Turn on the mood scene in the living room”). A topic with unclear: true catches sentences whose words do not fit together. The model guesses what was said - it knows the names of rooms and actions - and the assistant asks: “I'm not sure I heard you right. Did you mean: turn on the mood scene in the living room?”. On “yes” the corrected sentence goes through the whole normal path (HA sentences, automations, router); on “no” the assistant asks you to repeat, and “cancel” ends the conversation. When no guess is possible, it says straight away “I didn't understand. Please repeat.” In the topic description it is worth stating explicitly what does not belong here: questions and commands with one garbled word when the meaning is clear, knowledge questions, chit-chat. Nothing is executed without confirmation. The assistant asks you to repeat at most once in a row. If it fails to understand a second time (gibberish again, or “no” to its suggestion again), it says “Sorry, I don't understand. If you need anything, just ask me again.” and ends the conversation - the microphone closes. Every command or question that is understood resets the counter; each conversation (speaker) is counted separately.
  9. Safeguards.
    • Alarm only via sentences. A command with alarm words (Polish pack: „alarm”, „czuwanie”, „ochrona”, „syrena”, „uzbrój”, „rozbrój”, also garbled, e.g. „halaryn”) that was not caught by an automation with sentences does not go to the model - the assistant replies with a hint (“I only control the alarm with specific sentences, for example: turn off the alarm…”). Testing showed that the model could otherwise pick the “Good morning” scene.
    • No room - the speaker's room. For a command without an area and without a name (“turn off the light”), HA takes all devices of that kind in the home. So the integration adds the room of the speaker the command came from; if the speaker is unknown, it asks “In which room?”. (In testing, a garbled “turn off the alarm” once turned off 64 lights this way.)
    • Large scope. More than 8 devices at once without “all”, “whole”, “every” in the command - a question first.
    • Guessed device type. When the model chose e.g. a light, but the command has neither a device name nor a word that points to a light (“turn off the cauliflower in the kitchen”) - the question “Do I understand correctly…?”.
    • A device that does not respond. When the named device (or everything in the named room) is unavailable, nothing runs and the reply says why: “Urządzenie Skrzynka pocztowa nie odpowiada (jest niedostępne), więc nic nie zmieniłem.” (“The mailbox does not respond (unavailable), so I changed nothing.”). The same for a state question HA answers: instead of “Nie, … jest unavailable” - “…does not respond, so I don't know its state”. When only some devices do not respond, the command works on the others.
    • A plain “yes” with no question pending (“yes, do it”, “don't”) is not a command and does not run anything; “make it brighter in the living room” is a command, even though it starts with “make”.
    • An action is always run. “Turn off the TV and home cinema” may hit the script “TV - turn off” - and “turn off” on a script in HA would stop it. The model may also confuse a script and a scene - the name is looked up in both.
    • Script name without the model. Saying the exact name of a script or scene (at least 3 words, e.g. “Lower the inner blinds in the living room”) runs it immediately, without parsing by the model.
  10. “Play …” works differently. On a Music Assistant player: music_assistant.play_media - MA's own search with the media type (track, album, artist, playlist, podcast), the artist (“play Bohemian Rhapsody by Queen”) and radio mode (“play something like …”, endless similar music). On other players, for a genre, or when MA reports an error: a search (media_player.search_media) and playback of the first result. An empty list or unavailable players in the room - a reply that there is nothing to play on. The code chooses the player: from music_players (first available); without an entry, a player with search support in that area or with the room name in its name; and with no room in the command, the satellite's room. A light without color or color temperature support gets a message instead of an error.
  11. Music without a title (“turn on the music”, “play something in the kitchen”, “resume the music”) resumes the queue of the room's player from music_players (or the satellite's room). With music_players set, music plays only on those players - a satellite's own speaker named in the command is ignored.
  12. “Turn off the music [in …]” pauses the players that are playing in that room (HassMediaPause) instead of turning devices off: a Music Assistant player cannot be turned off, and turning off a HomePod (Apple TV integration) or a satellite's speaker does not stop the music. “Turn off the TV” still turns it off. The music words are MUSIC_WORDS in the language pack.
Scope. The router controls everything that is exposed to Assist. Put devices you do not want switched without a question (servers, the fridge) in confirm_entities, and do not expose those you never want controlled by voice.

12. Testing and choosing models

The tools/ directory contains five tools (Python, run from any computer with access to Ollama):

  • snapshot_data.py saves a snapshot of real data: Wikipedia articles and, for cases with a topic (topic, question, speaker), the topic data exactly as the integration builds it: entities, details and fetch, with the person and day from the question (needs --router-config). It also stores the snapshot time, which the model gets as "now", so the expected facts in the test do not change.
  • model_benchmark.py tests models in turn:
    • router, with the same prompt as the integration;
    • answers from data;
    • summaries.
    Scoring is automatic: required and forbidden fragments, and length. The control section checks command parsing against the home snapshot, without executing anything. It replays the integration's whole decision: the alarm safeguard, a plain “yes/no” reply, the script name without the model, and parsing with the list of actions (scripts with descriptions, scenes). It checks the intent, the area, the matched device or action, and whether the assistant would ask for confirmation. snapshot_data.py --only-home refreshes just the home snapshot, e.g. after changing descriptions or aliases. The code tests alone (pytest) check control from sentence to the called service on a fake home (tests/test_actions.py). The --rescore option re-scores saved answers after test fixes. A section without its own system prompt uses the integration's prompts: answers get the topic data with the speaker and the hint, summaries (prompt: summary) the summary prompt. In the router part an ambiguous question may list several equally good topics. For a long run over many models: --pull downloads missing models (the next one already in the background), --delete-after removes them after their test (never models installed before the start; --keep protects more), and --resume skips models that already have all results, so an interrupted run can be resumed.
  • model_report.py creates an HTML report and appends history to a CSV, so new models can be compared with old ones.
  • compare_sources.py is a consistency test for changing a topic's data source. For each question in a list it computes the data the old way and the new way (two router.yaml files), e.g. automation sentences versus details/fetch, on live HA data. It saves the model's answers side by side. Read-only.
  • check_sentences.py checks your automations with sentences. From each conversation trigger template it generates a few sentences and asks HA (debug mode, nothing is executed) what would handle them. It reports sentences that hit a different automation or HA intent, sentences that match nothing, and disabled automations. Run it after every change to your sentences.
.venv/bin/python tools/model_benchmark.py --ollama http://localhost:11434 \
  --router-config /config/assist/router.yaml --cases model_test.yaml \
  --data model_test_data.yaml --router gemma4:e4b --answer gemma4:26b --pull --out results.json
.venv/bin/python tools/model_report.py results.json --label "test" \
  --html result.html --csv model_results.csv --answers-csv model_answers.csv
.venv/bin/python tools/compare_sources.py --ha http://homeassistant.local:8123 \
  --token-file ~/.ha_token --ollama http://localhost:11434 \
  --old router.yaml --new router.new.yaml --questions questions.txt --out comparison.json
.venv/bin/python tools/check_sentences.py --ha http://homeassistant.local:8123 \
  --token-file ~/.ha_token --config /config --per-template 5

The test case file (YAML) contains questions with the expected topic, and data with a question and the expected facts. The format is described at the top of tools/model_benchmark.py. Keep it outside the repository, because it contains your home's data. The test questions are in the language of your pack (Polish for the bundled one); a new language pack is checked the same way.

13. Fine-tuning the router (optional)

A general small model recognizes topics well, but it can be fine-tuned on your own home's data. This is done with a separate set of scripts that will move to a separate repository in the future. Training requires a graphics card (e.g. an RTX 4090), and after fine-tuning the model runs in Ollama like any other. Steps:

  1. fetching areas, entities with aliases, people and sentence files from HA;
  2. the dataset:
    • sentences from your hassil templates, with the topic assigned via the template questions in router.yaml;
    • built-in HA intents with your names;
    • knowledge questions;
    • Whisper-style noise.
  3. LoRA (Unsloth) with exactly the same prompt the integration uses;
  4. export to Ollama;
  5. a test on questions that were not in the training data.

After the topic list changes, the fine-tuned model has to be fine-tuned again.

Lessons from the first attempt: Gemma 4 E2B fine-tuned on template sentences alone recognized them 99% of the time, but on free-form questions from the log it did worse than plain Gemma 4 E4B (88/96 versus 93/96). It learned the style of the templates, not the language. That is why the second run combines templates with paraphrases written by a large model (Gemma 4 26B): natural questions with names, rooms and Whisper errors. The base is E4B.

14. Privacy and security

  • Everything runs locally: HA, Ollama, Whisper and Piper. The only thing sent to the internet is the search term from knowledge questions (e.g. “Nicolaus Copernicus”), sent to the Wikipedia API.
  • Only the data of the topic asked about goes to the model: the entities, attributes and service responses listed in router.yaml, trimmed to the person and day. With only_exposed: true these are exclusively entities exposed to Assist.
  • A question never switches anything. fetch only calls services that only return data. Control goes exclusively through the control: true topic and HA intents, which check whether entities are exposed. Uncertain commands, locks, gates and devices in confirm_entities require confirmation.
  • The CSV file contains what household members said. If you do not need it, turn logging off in the options.

15. Adding a language

Everything that depends on a language lives in one language pack: a Python module in custom_components/assist_router/languages/ named after the language code. The integration ships the Polish pack, pl.py. It holds:

  • the spoken replies (confirmations, errors, “Did you mean…?”, announcement and speaker messages);
  • the words and patterns used to understand commands and questions: day words (mapped to day codes), yes / no / cancel replies and correction lead-ins („pytałem czy” – REPHRASE_LEADS), verbs, colors, first-person words, family terms, announcement and alarm keywords, Whisper corrections, the beginnings of knowledge questions;
  • the LLM prompts (router, answer, summary, control, guessing, example sentences) and the JSON key names they ask for (TOPIC_KEY, CONTROL_KEYS…);
  • log labels, state names and a few functions that build sentences (they depend on grammar), plus CODE and the default WIKIPEDIA_LANGUAGE.

To add, for example, Czech:

  1. Copy languages/pl.py to languages/cs.py.
  2. Translate all phrases, patterns, prompts and replies. Keep the same names of constants and functions (and their arguments) - the code reads them through LANG. JSON key names can be translated too (optional; a model fills in keys in its own language more reliably). Set CODE = "cs" and WIKIPEDIA_LANGUAGE = "cs".
  3. Day codes stay the same. The codes used in days: and in the when variable (today, tomorrow, day_after_tomorrow, weekend, week, monday … sunday, a number of days) are keywords and the same in every language. The new pack maps the spoken Czech words to them (WHEN_PATTERNS) and may add its own names for days: (DAY_ALIASES, like Polish dzis, jutro); the alias of when in COMMAND_VARIABLE_ALIASES (Polish kiedy) then gets those names.
  4. The pack is used when Home Assistant's language is cs, or when router.yaml has language: cs. The conversation agent then also lists Czech among its supported languages. An unknown code in language: disables the router with an error in the log.
  5. Choose an Ollama model that understands and writes the language well - the router, the answers and command parsing all happen in that language.
  6. Write router.yaml descriptions, examples and match patterns in Czech, and test with tools/model_benchmark.py using Czech test questions (section 12).
